Connecting an On-Premises Data Source to Microsoft Fabric Using Private Link Service Direct Connect

My hands-on journey connecting a Microsoft Fabric Notebook to an on-premises SQL Server

Recently, I wanted to solve a simple problem:

How can I connect a Microsoft Fabric Notebook to an on-premises SQL Server securely, without exposing the SQL Server to the public internet?

I expected this to be mostly a JDBC configuration.

It wasn’t. 😄

What started as a database connectivity task turned into a great hands-on learning experience involving Microsoft Fabric, Azure Private Link, Private Link Service Direct Connect, DNS, networking, Linux, SQL Server, and PySpark JDBC.

This post captures what I learned along the way.

The goal

The end goal was:

Microsoft Fabric Notebook  →  Managed Private Endpoint  →  Private Link Service Direct Connect  →  Private network connectivity  →  VPN / ExpressRoute  →  On-Premises SQL Server

I wanted the SQL Server to remain private and accessible only through the private networking path.

1. Understanding the architecture

The first thing I learned was that there are several different components involved.

At a high level:

  • Fabric Notebook needs to reach the Managed Private Endpoint.
  • The Managed Private Endpoint connects to an Azure Private Link Service.
  • The Private Link Service provides the private connection toward the destination.
  • For an on-premises scenario, the Azure environment also needs private connectivity to the on-premises network, typically through VPN or ExpressRoute.

The important part is that the network path needs to work end-to-end.

2. Private Link Service Direct Connect

While researching the architecture, I came across Private Link Service Direct Connect. (Public Preview)

This was particularly interesting because the traditional architecture can require additional Azure components such as an Internal Load Balancer and forwarding VMs.

With Direct Connect, the architecture can be simplified for suitable scenarios where the destination has a static private IP.

Conceptually:

Fabric → Private Link Service → Direct Connect → Private network → On-Prem SQL

Microsoft currently documents Direct Connect as a Public Preview capability, so it is important to check regional availability and the latest Microsoft documentation before using it in production.

3. Enabling the Azure feature

One of the prerequisites I encountered was the Azure feature flag:

Microsoft.Network/AllowPrivateLinkserviceUDR

I registered it using Azure CLI:

az feature register \
  --namespace Microsoft.Network \
  --name AllowPrivateLinkserviceUDR

Then I checked the status:

az feature show \
  --namespace Microsoft.Network \
  --name AllowPrivateLinkserviceUDR \
  --query "properties.state" \
  -o tsv

The status needs to eventually show:

Registered

I also registered the Microsoft.Network provider:

az provider register --namespace Microsoft.Network

This was a good reminder that Azure preview networking capabilities can have additional subscription-level prerequisites.

4. Testing the network before Fabric

One of the biggest lessons from this exercise was:

Don’t start with Fabric. Start with the network.

Before troubleshooting the Fabric Notebook, I tested connectivity from an Azure Ubuntu machine toward the SQL Server.

For example:

nc -vz <SQL_SERVER_IP> 1433

or:

telnet <SQL_SERVER_IP> 1433

SQL Server’s default TCP port is:

1433

If this test fails, there is no point troubleshooting JDBC or Fabric yet.

The problem is somewhere in:

Azure VM → VPN / ExpressRoute → On-Prem Network → Firewall → SQL Server

5. DNS

I also wanted to use a hostname instead of an IP:

sqlserver.corp.clouddusk.local

From Ubuntu, I could test DNS resolution with:

getent hosts sqlserver.corp.clouddusk.local

or:

nslookup sqlserver.corp.clouddusk.local

For temporary Ubuntu testing, an /etc/hosts entry can be used:

<PRIVATE_IP> sqlserver.corp.clouddusk.local

Then:

getent hosts sqlserver.corp.clouddusk.local

One important lesson here:

/etc/hosts only affects that machine.

It doesn’t automatically provide DNS resolution to Microsoft Fabric.

For production, DNS needs to be designed as part of the overall private connectivity architecture.

6. Creating the Fabric Managed Private Endpoint

I used the Fabric REST API to create the Managed Private Endpoint.

The endpoint is:

POST https://api.fabric.microsoft.com/v1/workspaces/{workspaceId}/managedPrivateEndpoints

The request body looked like:

{
  "name": "onprem-sql-endpoint",
  "targetPrivateLinkResourceId": "<PRIVATE_LINK_SERVICE_RESOURCE_ID>",
  "targetFQDNs": [
    "sqlserver.corp.clouddusk.local"
  ],
  "requestMessage": "Private connection request from Fabric to on-premises SQL"
}

I tested this API using Hoppscotch, which was convenient because it allowed me to test the REST API directly from the browser.

The request uses a Microsoft Entra access token:

Authorization: Bearer <ACCESS_TOKEN>

and:

Content-Type: application/json

7. An interesting error I encountered

Initially, I included:

"targetSubresourceType": "sql"

The API returned:

InvalidTargetSubResourceType

That was a useful lesson.

Instead of guessing values such as sql, sqlServer, etc., I went back to the target resource configuration.

For my Direct Connect Private Link Service scenario, removing the unnecessary property allowed the Managed Private Endpoint to provision successfully.

The final request was:

{
  "name": "onprem-sql-endpoint",
  "targetPrivateLinkResourceId": "<PRIVATE_LINK_SERVICE_RESOURCE_ID>",
  "targetFQDNs": [
    "sqlserver.corp.clouddusk.local"
  ],
  "requestMessage": "Private connection request from Fabric to on-premises SQL"
}

Approve the Private Link Connection from Azure

Once the Managed Private Endpoint is created in Microsoft Fabric, the corresponding connection request appears on the Azure Private Link Service.

From the Azure Portal, navigate to:

Private Link Service → pls-directconnect001 → Settings → Private endpoint connections

The new connection initially requires approval from the Private Link Service owner.

In my case, the connection request appeared in the list with the Connection state ready for approval.

I selected the connection and clicked Approve.

After approval, Azure shows:

  • ✅ Connection state: Approved
  • ✅ The associated Fabric private endpoint is listed
  • ✅ The connection is ready for the Fabric Managed Private Endpoint to use

This approval establishes the private link between the Microsoft Fabric Managed Private Endpoint and the Azure Private Link Service.

The next step is to verify the connection from the Fabric workspace and then test connectivity to the on-premises SQL Server from a Fabric Notebook.

8. Verifying the Managed Private Endpoint

After creating the endpoint, I used the Fabric REST API to check the endpoint.

For example:

GET https://api.fabric.microsoft.com/v1/workspaces/{workspaceId}/managedPrivateEndpoints

The important things to verify are:

  • Endpoint name
  • Provisioning state
  • Connection state
  • FQDN
  • Private Link resource ID

The endpoint needs to be successfully provisioned and the Private Link connection needs to be approved.

Verify the Managed Private Endpoint

After creating the managed private endpoint, I verified it from the Fabric workspace:

Workspace → Workspace settings → Network security → Managed private endpoints

As shown below, my endpoint onprem-sql-endpoint001 shows:

  • ✅ Activation: Succeeded
  • ✅ Approval: Approved

This confirms that the Managed Private Endpoint has been successfully provisioned and the Private Link connection has been approved.

With the endpoint approved, the next step is to validate end-to-end connectivity from the Fabric Notebook to the on-premises SQL Server using JDBC.

9. Testing SQL Server from Ubuntu

Once the network path was available, I installed sqlcmd on Ubuntu.

This was useful because telnet and nc only tell me whether TCP connectivity exists.

sqlcmd actually tests SQL Server.

For example:

sqlcmd \
  -S sqlserver.corp.clouddusk.local,1433 \
  -U <SQL_USER> \
  -P '<SQL_PASSWORD>'

Once connected:

SELECT @@SERVERNAME;GO

This gave me much more confidence that the complete network path to SQL Server was working.

10. Connecting from the Fabric Notebook

Once the network connectivity was working, the Fabric Notebook code was relatively straightforward.

I used JDBC:

serverName = "sqlserver.corp.clouddusk.local"
database = "AdventureWorksLT2017"
dbPort = 1433

jdbcURL = (
    f"jdbc:sqlserver://{serverName}:{dbPort};"
    f"databaseName={database};"
    "encrypt=true;"
    "trustServerCertificate=true"
)

connectionProps = {
    "user": "<SQL_USER>",
    "password": "<SQL_PASSWORD>",
    "driver": "com.microsoft.sqlserver.jdbc.SQLServerDriver"
}

Then I could read a SQL Server table:

df = spark.read.jdbc(
    url=jdbcURL,
    table="SalesLT.Customer",
    properties=connectionProps
)
display(df)

11. A database error that turned out not to be networking

At one point I received:

SQLServerException: Invalid object name 'dbo.Customers'

This initially looked like another connectivity problem.

It wasn’t.

The JDBC connection was already successful.

The problem was simply that I was using the wrong table name.

The AdventureWorksLT database uses:

SalesLT.Customer

rather than:

dbo.Customers

So changing the table to:

table="SalesLT.Customer"

resolved the problem.

This was probably one of the most useful lessons from the entire exercise:

Once JDBC successfully reaches SQL Server, stop troubleshooting the Azure network. Start looking at the database, schema, table, authentication, and permissions.

12. Writing the data into the Fabric Lakehouse

Once I successfully loaded the SQL Server data into a Spark DataFrame, I could write it into the Fabric Lakehouse as a Delta table.

df.write \
    .mode("overwrite") \
    .format("delta") \
    .saveAsTable("Customers")

So the complete flow became:

On-Prem SQL Server → Private networking → Fabric Managed Private Endpoint → Fabric Notebook → JDBC → Spark DataFrame → Fabric Lakehouse → Delta Table

13. My troubleshooting checklist

If I had to do this again, I would troubleshoot in this exact order.

1. DNS

getent hosts sqlserver.corp.clouddusk.local

2. TCP

nc -vz sqlserver.corp.clouddusk.local 1433

3. SQL Server

sqlcmd -S sqlserver.corp.clouddusk.local,1433

4. Private Link

Verify: Managed Private Endpoint → Provisioned → Connection Approved

5. JDBC

spark.read.jdbc(...)

6. Database

Verify: Database → Schema → Table → Permissions

This layered approach prevents spending hours changing Fabric settings when the real problem is DNS or SQL Server.

What I learned

This project taught me much more than just how to connect Fabric to SQL Server.

The biggest lessons were:

  1. Cloud networking is layered. DNS, routing, TCP, Private Link, authentication, JDBC, and the database are separate layers.
  2. Test each layer independently. nc, telnet, sqlcmd, and JDBC each answer a different question.
  3. Private Link Service Direct Connect can simplify the architecture. For suitable static-IP scenarios, it can remove the need for the traditional Load Balancer + forwarding VM pattern.
  4. Fabric REST APIs are useful. I was able to create and inspect the Managed Private Endpoint using the Fabric API.
  5. Browser-based API tools are handy. Hoppscotch was enough to test the Fabric REST API without installing Postman.
  6. Not every JDBC error is a network error. Invalid object name 'dbo.Customers' turned out to be a schema/table issue after the network connection was already working.

Final architecture

Microsoft Fabric
  → Fabric Notebook
  → Managed Private Endpoint
  → Private Link Service Direct Connect
  → Private IP routing
  → VPN / ExpressRoute
  → On-Prem Network
  → SQL Server :1433
  → AdventureWorksLT2017
  → SalesLT.Customer
  → Fabric Lakehouse

Final thoughts

What started as:

“I just need Fabric to read a SQL Server table”

ended up being a great hands-on lesson in private cloud networking.

The most valuable part wasn’t the final JDBC code. It was understanding the path that the data takes before JDBC ever gets a chance to run.

Once the network path was working, the actual Fabric Notebook code was the easy part.
